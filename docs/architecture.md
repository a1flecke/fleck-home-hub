# Architecture

Fleck Home Hub is a modular monolith. Routes and Svelte components call server-side application logic; domain policies do not import presentation or database modules. Infrastructure provides SQLite, Better Auth and external integrations. Only create interfaces for real extension points. Host-authorized first run, resumable household progress, and parent-managed child identities reuse the existing Better Auth session and membership model. See [ADR 0005](adr/0005-family-onboarding.md). Notifications are a future domain. Household expense planning is a separate parent-only domain, with bounded household-local recurrence projections; recorded expense payments preserve immutable history, and the expense page remains future work. See [expenses.md](expenses.md). The server-side weather integration for the family display uses an in-process cache, background refresh, retries and a circuit breaker; cross-process caching is not implemented. See [weather.md](weather.md) and [ADR 0002](adr/0002-weather-refresh-reliability.md).

Meals are household-scoped records managed by parents. The planner reads at most one household-local seven-day week; moves and removals recheck parent membership and household ownership in an immediate transaction. Repeating a meal reads a bounded recent-meal list without notes, previews the copy, and creates a separate private row through the existing submission-key idempotency. Shopping a week reviews ingredient lines across one seven-day plan, revalidates the meals and active grocery list in one immediate transaction, and stores a confirmation key so retries cannot duplicate rows. The shared display shows only explicitly shared meals and excludes private notes; children can view shared meals in the weekly view. Recipe links are user-provided HTTPS URLs. A small provider registry recognizes exact approved hosts for credit and link labels. A parent may explicitly preview one recognized eMeals link; the server fetches only that URL, extracts yield, total time and ingredient lines from JSON-LD, and never reads directions or images. Share-target drafts are rendered without writing a row, and a submission key makes Save retries idempotent. See [meals.md](meals.md) and [ADR 0003](adr/0003-emeals-recipe-preview.md).

The dependency test in `tests/architecture/dependencies.test.ts` runs dependency-cruiser against `src` and checks its rules with synthetic positive and negative examples. Domain modules in `src/lib/chores`, `src/lib/earnings`, `src/lib/grocery` and `src/lib/expenses` may depend on one another but not on other modules or platform packages. Server modules must not import routes, client components and universal page/layout modules must not import server runtime code, and the discovered source graph must have no cycles. A deliberately unresolved `$lib` alias is rejected: SvelteKit 3 removed its default definition, so if the project introduces an alias its configuration and tests must change together. The graph does not prove all architecture properties: Svelte preprocessing may erase type-only imports; computed dynamic imports, other unresolved aliases, framework-generated modules and external package internals need separate review. SvelteKit's server-only checks and the typechecker remain necessary.

Use consistent domain terms across code, tests, and UI. A **submission** is a child's request for review, not earned money. **Pending verification** describes submitted work awaiting a parent; **needs rework** means it can be submitted again; **verified** means a parent accepted it. An **earning credit** records a paid verification, while a **payout** records a payment already made; neither is a pending reward. The state-transition and SQLite integration tests protect the meanings and financial invariants; the dependency graph cannot infer domain semantics.

Identity uses Better Auth sessions and a `membership` row mapping a user to a household and role. Protected requests resolve the session server-side and check membership for the requested household. A missing session, membership, configuration or database denies access. The shared display accepts either a member session or a separate, revocable display credential that no other route accepts ([ADR 0004](adr/0004-restricted-display-sessions.md)), and shows only parent-selected event and chore titles and limited status details; descriptions, locations, assignees and finances are excluded. Its sharing page lists only records in the display window plus a paginated list of other current selections ([ADR 0007](adr/0007-bounded-display-sharing-choices.md)). The public landing page remains a synthetic preview. Network access through Tailscale is not authorization.

The calendar stores household-local event dates and wall times, optional recurring weekdays and cancelled occurrences. Household members may read it; only parents may manage events and the to-schedule inbox. Scheduling an inbox item creates its event and closes the item in one transaction. The dashboard reads a bounded seven-date projection containing only the fields needed by its Coming up card. See [calendar.md](calendar.md) for DST limitations and the migration procedure.

My Day projects the next seven dinners for parents with direct planner links; a child's My Day projects only shared meals without notes or management actions, using the same bounded week read as the weekly meal view. The shared display keeps its separate shared-only projection. A child's chore completion is a submission pending parent verification. A parent may verify it or return it for rework. A SQLite immediate transaction checks household membership and the state transition, writes an actor/timestamp audit record, and on paid verification inserts one credit with a unique chore association. The ledger stores integer cents, rejects updates and deletes, and preserves the amount at verification. Pending rewards are calculated separately from verified credits; balances are sums of ledger entries. Repeated approvals are rejected.

Parents may correct or cancel an unstarted one-time chore from the weekly board. The verification state machine and its status CHECK remain unchanged: cancellation is a separate lifecycle marker (`cancelled_at`/`cancelled_by`) recorded with the actor and changed fields in `chore_revision`. An immediate transaction rechecks active parent membership, rejects recurring occurrences, started work and cancelled rows, and compares the update-time token the form was loaded with so a stale edit cannot overwrite newer work. Cancelled chores are excluded from chore scopes, the weekly board and the display projection, and the existing transition guard rejects submission; no earning is created and no row, transition or financial record is deleted.

Parents may record payments already made; the app transfers no money. Payouts are immutable, household-scoped records with an actor, payment date, amount and request ID. A SQLite immediate transaction checks authorization, idempotency, that the payment date is not after the household-local date, and the current owed amount before inserting a payout, preventing competing payments from exceeding verified credits. A parent can correct a mistaken payout using a single immutable full reversal with a reason; neither the original payout nor its reversal can be changed or deleted. Owed is verified credits minus non-reversed payouts. Paid so far is the net of recorded payouts and reversals; pending chore submissions do not contribute to the owed amount. An optional weekly or biweekly payday is a household-local reminder and never creates a payout.

Recurring definitions use household-local calendar dates and selected weekdays; all weekdays means daily and one weekday means weekly. The household time zone defaults to America/Chicago and a parent can change it. On a dashboard visit the server generates today and the next seven days inside an immediate transaction. A unique series/date key prevents duplicate occurrences even across processes. Each occurrence is an ordinary chore with its own reward and verification history; future unstarted chores may be edited, while today's and historical chores retain their existing values. To change the recurrence days or date range, end the series and create another. The parent-only weekly board at `/chores/week` reads exactly one bounded Sunday-to-Saturday range, groups it by day and child, and generates occurrences only from today or a future selected start through that week's end. It never backfills a past week; historical gaps remain a separate recovery decision.

There is no background scheduler or automatic backfill. Parents can review bounded historical gaps and explicitly create an unverified late occurrence or record a skip. The recovery decision and its actor are recorded in the same transaction as the occurrence or skip. Forward pause records capture the dates from pausing up to, but excluding, the day the series resumes. Historical gaps require human review because past pause, assignee and reward data may be incomplete. Previously generated overdue chores remain available unless skipped. Pausing hides and blocks unstarted current and future occurrences; on resumption, generated unstarted dates that elapsed during the pause are skipped. Ending a series prevents future generation and hides its unstarted current and future occurrences. A skipped occurrence cannot be submitted and creates no earnings. Submitted work remains subject to normal verification, even when its series is paused or ended. Only a parent may manage schedules, exceptions, or the time zone.

My Day is a bounded overview rather than a complete history. Actionable chores are split into bounded review, overdue, today, upcoming, later and rework sections; verified work shows only a recent preview. Aggregate counts and ledger balances cover every matching record, while `/chores/history`, `/chores/series` and `/earnings/[childId]` provide paginated access to complete histories and schedule management. The `later` scope keeps far-future work reachable. See [ADR 0006](adr/0006-bounded-my-day-history.md).

Parents review completed chores at `/verify`, grouped by child and submission date and paginated across all pending submissions. Pending rewards are shown separately from verified earnings. Verifying or returning work calls the same transactional chore service as the rest of the application; a rework decision requires a reason and creates no credit, while verification creates at most one immutable credit. There is no automatic or bulk approval.

A child's My Day uses the same bounded chore sections but presents them for a phone or tablet: **To do today** first, then needs rework, overdue, awaiting approval, coming up, later and recently completed. Completion actions are large native forms, feedback is encouraging without implying pending work is earned, and the earnings summary separates pending rewards from verified money owed. Children see only their own chores and ledger; no sibling financial data, parent review controls, series management or bulk actions are projected into this view.

The checked-in Better Auth SQLite baseline is followed by the checked-in Drizzle household migration. The installed Better Auth version is pinned; its migration planner is used to detect missing schema changes, not to apply them. Existing authentication tables must match the reviewed baseline's columns, foreign keys and unique constraints. The authentication and household migrations use separate transactions, so keep a verified backup before migrating. Authentication configuration and database files are local private state, never fixtures or repository files.
