# Architecture

Fleck Home Hub is a modular monolith. Routes and Svelte components call server-side application logic; domain policies do not import presentation or database modules. Infrastructure provides SQLite, Better Auth and external integrations. Only create interfaces for real extension points. Notifications, groceries, expenses and weather are future domains, not implemented services.

Meals are household-scoped records managed by parents. The shared display shows only explicitly shared meals and excludes private notes; children can view shared meals. Recipe links are user-provided HTTPS URLs and are never fetched by the server. See [meals.md](meals.md).

The dependency test in `tests/architecture/dependencies.test.ts` runs dependency-cruiser against `src` and checks its rules with synthetic positive and negative examples. Domain modules in `src/lib/chores`, `src/lib/earnings` and `src/lib/grocery` may depend on one another but not on other modules or platform packages. Server modules must not import routes, client components and universal page/layout modules must not import server runtime code, and the discovered source graph must have no cycles. A deliberately unresolved `$lib` alias is rejected: SvelteKit 3 removed its default definition, so if the project introduces an alias its configuration and tests must change together. The graph does not prove all architecture properties: Svelte preprocessing may erase type-only imports; computed dynamic imports, other unresolved aliases, framework-generated modules and external package internals need separate review. SvelteKit's server-only checks and the typechecker remain necessary.

Use consistent domain terms across code, tests, and UI. A **submission** is a child's request for review, not earned money. **Pending verification** describes submitted work awaiting a parent; **needs rework** means it can be submitted again; **verified** means a parent accepted it. An **earning credit** records a paid verification, while a **payout** records a payment already made; neither is a pending reward. The state-transition and SQLite integration tests protect the meanings and financial invariants; the dependency graph cannot infer domain semantics.

Identity uses Better Auth sessions and a `membership` row mapping a user to a household and role. Protected requests resolve the session server-side and check membership for the requested household. A missing session, membership, configuration or database denies access. The shared display requires a session and shows only parent-selected event and chore titles and limited status details; descriptions, locations, assignees and finances are excluded. The public landing page remains a synthetic preview. Network access through Tailscale is not authorization.

The calendar stores household-local event dates and wall times, optional recurring weekdays and cancelled occurrences. Household members may read it; only parents may manage events and the to-schedule inbox. Scheduling an inbox item creates its event and closes the item in one transaction. See [calendar.md](calendar.md) for DST limitations and the migration procedure.

A child's chore completion is a submission pending parent verification. A parent may verify it or return it for rework. A SQLite immediate transaction checks household membership and the state transition, writes an actor/timestamp audit record, and on paid verification inserts one credit with a unique chore association. The ledger stores integer cents, rejects updates and deletes, and preserves the amount at verification. Pending rewards are calculated separately from verified credits; balances are sums of ledger entries. Repeated approvals are rejected.

Parents may record payments already made; the app transfers no money. Payouts are immutable, household-scoped records with an actor, payment date, amount and request ID. A SQLite immediate transaction checks authorization, idempotency and the current owed amount before inserting a payout, preventing competing payments from exceeding verified credits. A parent can correct a mistaken payout using a single immutable full reversal with a reason; neither the original payout nor its reversal can be changed or deleted. Owed is verified credits minus non-reversed payouts. Paid so far is the net of recorded payouts and reversals; pending chore submissions do not contribute to the owed amount. An optional weekly or biweekly payday is a household-local reminder and never creates a payout.

Recurring definitions use household-local calendar dates and selected weekdays; all weekdays means daily and one weekday means weekly. The household time zone defaults to America/Chicago and a parent can change it. On a dashboard visit the server generates today and the next seven days inside an immediate transaction. A unique series/date key prevents duplicate occurrences even across processes. Each occurrence is an ordinary chore with its own reward and verification history; future unstarted chores may be edited, while today's and historical chores retain their existing values. To change the recurrence days or date range, end the series and create another.

There is no background scheduler or retroactive backfill: dates not generated before a visit remain missed. Previously generated overdue chores remain available unless skipped. Pausing hides and blocks unstarted current and future occurrences; on resumption, generated unstarted dates that elapsed during the pause are skipped. Ending a series prevents future generation and hides its unstarted current and future occurrences. A skipped occurrence cannot be submitted and creates no earnings. Submitted work remains subject to normal verification, even when its series is paused or ended. Only a parent may manage schedules, exceptions, or the time zone.

The checked-in Better Auth SQLite baseline is followed by the checked-in Drizzle household migration. The installed Better Auth version is pinned; its migration planner is used to detect missing schema changes, not to apply them. Existing authentication tables must match the reviewed baseline's columns, foreign keys and unique constraints. The authentication and household migrations use separate transactions, so keep a verified backup before migrating. Authentication configuration and database files are local private state, never fixtures or repository files.
