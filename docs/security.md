# Security

Use HTTPS through a private tailnet, a unique random `AUTH_SECRET`, and a private database path. Parent and kid roles are checked by the server for each household. Public signup is disabled; local host access is required to run the account-provisioning commands. The authenticated shared display shows only parent-selected event and chore titles and limited status details. The public landing page shows synthetic data. The manifest does not implement offline synchronization.

## Restricted display sessions

A paired display holds a separate, revocable, read-only credential instead of a person's session: see [ADR 0004](adr/0004-restricted-display-sessions.md) for the invariants and threat model and [display](display.md) for pairing, revocation and recovery. It is a distinct credential type that no household route accepts, it is revoked when the pairing parent is disabled, and it needs no Better Auth account. Reaching the host over Tailscale is not authorization. An unlocked screen still discloses what it shows to anyone who can see it. This feature requires independent review before production use; the repository ruleset requires no approving reviews.

## Household invitation threat model

Initial bootstrap remains a trusted local operation. Public signup remains disabled. A signed-in parent may create a seven-day, single-use invitation for one household and one fixed role. The recipient creates a new account and chooses their own password; an existing email is rejected rather than linked or promoted. Parents should share links only through a trusted private channel. Anyone holding an unused link can redeem it before expiration or revocation, including a person who intercepts it. The parent can revoke a pending invitation in household settings; the issuer must still be a parent when it is redeemed.

The server stores a SHA-256 hash of a 256-bit random token, checks parent membership for each administrative action, and creates the credential, membership, and consumption record in one transaction. A child cannot choose a different role or manage invitations. A token for one household cannot grant access to another. The link contains the token in its fragment; invitation pages use no-store and an origin-only referrer policy. Avoid copying links into logs, support tickets, screenshots, or analytics. A stolen database, compromised host, malicious browser extension, or unlocked device is outside these protections.

An invalid token is rejected before expensive signup work; validity is checked again in the transaction. A maximum of two redemptions run simultaneously per process. A holder of a valid token can still consume resources, and this limit is not a distributed rate limiter. The worker uses the pinned Better Auth adapter transaction API and must be reviewed on upgrades.

Signing out revokes the current Better Auth session. Sessions default to seven days. Invitation revocation does not disable an account or revoke a session after redemption; use member disabling (with last-parent protection) and the personal session page at `/settings/sessions` for that. A user may have memberships in multiple households; account deletion must not be used to remove access to just one. Household selection in settings does not select a household across the rest of the application. Password reset and email recovery are not yet available; protect credentials and maintain verified backups. Validate private HTTPS, device sessions and recovery on the actual host and devices before household use.

SvelteKit sends a Content Security Policy for rendered pages restricting scripts, styles and connections to the application's origin, blocking objects and framing, and restricting form targets. SvelteKit adds nonces or hashes for its own generated inline content. HTTP localhost does not receive HSTS; HTTPS termination and HSTS policy remain deployment decisions requiring verification on the actual host and tailnet.

The native agent sandbox and approvals are primary controls. Claude's hook adds narrow checks, and malformed payloads exit 2, but command matching is not a shell parser and hook startup failures can be nonblocking. Git hooks are local safeguards, not an authoritative boundary; install them in each worktree. CI and configured branch protection must enforce checks independently. Never trust arbitrary command runners or use the project approval policy to weaken global restrictions.

Threats still requiring operational care include a stolen unlocked phone or session cookie, revoked tailnet access without session revocation, compromised host, filesystem access to the database or backups, and an unattended shared display. Parents can disable a member's access to one household and it applies to existing sessions ([household access](household-access.md)); each person can list and end their own sessions at `/settings/sessions`, but parents cannot end another member's sessions. There is no MFA yet. Protect the Mac, backups, and all devices. Do not use production household data until operational controls and remote behavior are verified.

In production, the pinned Better Auth version applies an in-memory limit of three sign-in requests per ten seconds. Forwarded IP headers are deliberately ignored until a trusted proxy boundary is verified, so sign-in attempts share a per-process bucket. This limits spoofed-header evasion but can temporarily throttle the whole household, resets on restart, and is not coordinated across processes. Development and test do not enable this production default. Do not trust a proxy-supplied address without verifying how the proxy strips and reconstructs client headers. Sessions use Better Auth's default seven-day expiry and are revoked at sign-out; real HTTPS cookie behavior and device session persistence remain unverified.

CI runs zizmor, Gitleaks and `pnpm audit --audit-level moderate`; low-severity advisories also need review. PRs run without production secrets. On 2026-10-29, the live GitHub ruleset required the stable `merge-gate` check on `main`, with no bypass actors. Repository files do not enforce that setting; administrators should verify it remains active. The gate and workflow are PR-controlled, so a passing check does not replace review of changes to them. See `docs/foundation-audit-2026-10-29.md`.

pnpm requires registry releases to be at least 72 hours old, including transitive dependencies; it fails rather than falling back to a younger release or accepting missing publication times. Frozen installs revalidate lockfile entries against this policy, which can require registry access. Exotic transitive sources are blocked. Dependency install scripts are denied unless explicitly approved: currently only `esbuild` is allowed for its platform binary. The pinned `better-sqlite3` includes prebuilt binaries and does not declare an install lifecycle script. Review changes to the allowlist, dependency versions and policy exceptions together; a cooldown reduces exposure but does not establish that a package is safe.

The current ruleset requires no approving reviews. `.github/CODEOWNERS` identifies sensitive paths but does not enforce approval by itself, and the sole listed maintainer cannot independently approve their own PR. To create a review boundary, add a separate trusted reviewer with repository access, make them a code owner for the sensitive paths, and configure the main ruleset to require code-owner approval and at least one approval, dismiss stale approvals, and restrict bypass. Verify the effective rules and test a PR touching a protected file. If a second reviewer is unavailable, use a separately administered GitHub App or external CI policy service whose required check and credentials are not controlled by this repository or PR author. Neither a PR-controlled workflow nor self-review provides independent protection. Limit agent tokens and app installations to the least permissions needed and keep ruleset administration outside the agent's authority.

On 2026-10-29, the active `Protect main` ruleset was rechecked: it requires pull requests and the GitHub Actions `merge-gate` with strict status checks, has no bypass actors, and blocks deletion and non-fast-forward updates. It still requires zero approving reviews and does not require code-owner review. To change that, a repository administrator must edit the `Protect main` ruleset under Settings → Rules → Rulesets, set at least one approval, enable code-owner review and stale-review dismissal, retain the existing required check and restrictions, and assign an eligible independent reviewer in CODEOWNERS. Verify enforcement with a test PR touching a protected path. If no independent reviewer exists, use the separately administered external check described above; do not configure the author as a substitute for independent approval.

The dependency audit on 2026-10-31 reported low GHSA-gcqx-w48m-w2h4 in deepmerge, with no published fix. The Svelte Vite plugin uses it to merge local build configuration; do not feed untrusted configuration into the build. Reassess when an upstream fix is available. The unused Drizzle Kit CLI and its vulnerable esbuild loader have been removed, including the optional peer installed by Better Auth; the reviewed migrations still run through Drizzle ORM. A temporary minimatch override resolves GHSA-g3hv-75wg-m249; remove it when ESLint and its dependencies support a fixed version natively. Review both overrides when upgrading their parents.
