# Security

Use HTTPS through a private tailnet, a unique random `AUTH_SECRET`, and a private database path. Parent and kid roles are checked by the server for each household. Public signup is disabled; local host access is required to run the account-provisioning commands. Shared displays show synthetic data only. The manifest does not implement offline synchronization.

SvelteKit sends a Content Security Policy for rendered pages restricting scripts, styles and connections to the application's origin, blocking objects and framing, and restricting form targets. SvelteKit adds nonces or hashes for its own generated inline content. HTTP localhost does not receive HSTS; HTTPS termination and HSTS policy remain deployment decisions requiring verification on the actual host and tailnet.

The native agent sandbox and approvals are primary controls. Claude's hook adds narrow checks, and malformed payloads exit 2, but command matching is not a shell parser and hook startup failures can be nonblocking. Git hooks are local safeguards, not an authoritative boundary; install them in each worktree. CI and configured branch protection must enforce checks independently. Never trust arbitrary command runners or use the project approval policy to weaken global restrictions.

Threats still requiring operational care include a stolen unlocked phone or session cookie, revoked tailnet access without session revocation, compromised host, filesystem access to the database or backups, and an unattended shared display. Sessions are revocable, but there is no account-management UI or MFA yet. Protect the Mac, backups, and all devices. Do not use production household data until operational controls and remote behavior are verified.

In production, the pinned Better Auth version applies an in-memory limit of three sign-in requests per ten seconds. Forwarded IP headers are deliberately ignored until a trusted proxy boundary is verified, so sign-in attempts share a per-process bucket. This limits spoofed-header evasion but can temporarily throttle the whole household, resets on restart, and is not coordinated across processes. Development and test do not enable this production default. Do not trust a proxy-supplied address without verifying how the proxy strips and reconstructs client headers. Sessions use Better Auth's default seven-day expiry and are revoked at sign-out; real HTTPS cookie behavior and device session persistence remain unverified.

CI runs zizmor, Gitleaks and `pnpm audit --audit-level high`; lower-severity advisories also need review. PRs run without production secrets. On 2026-10-29, the live GitHub ruleset required the stable `merge-gate` check on `main`, with no bypass actors. Repository files do not enforce that setting; administrators should verify it remains active. The gate and workflow are PR-controlled, so a passing check does not replace review of changes to them. See `docs/foundation-audit-2026-10-29.md`.

pnpm requires registry releases to be at least 72 hours old, including transitive dependencies; it fails rather than falling back to a younger release or accepting missing publication times. Frozen installs revalidate lockfile entries against this policy, which can require registry access. Exotic transitive sources are blocked. Dependency install scripts are denied unless explicitly approved: currently only `esbuild` is allowed for its platform binary. The pinned `better-sqlite3` includes prebuilt binaries and does not declare an install lifecycle script. Review changes to the allowlist, dependency versions and policy exceptions together; a cooldown reduces exposure but does not establish that a package is safe.

The current ruleset requires no approving reviews. `.github/CODEOWNERS` identifies sensitive paths but does not enforce approval by itself, and the sole listed maintainer cannot independently approve their own PR. To create a review boundary, add a separate trusted reviewer with repository access, make them a code owner for the sensitive paths, and configure the main ruleset to require code-owner approval and at least one approval, dismiss stale approvals, and restrict bypass. Verify the effective rules and test a PR touching a protected file. If a second reviewer is unavailable, use a separately administered GitHub App or external CI policy service whose required check and credentials are not controlled by this repository or PR author. Neither a PR-controlled workflow nor self-review provides independent protection. Limit agent tokens and app installations to the least permissions needed and keep ruleset administration outside the agent's authority.

On 2026-10-29, the active `Protect main` ruleset was rechecked: it requires pull requests and the GitHub Actions `merge-gate` with strict status checks, has no bypass actors, and blocks deletion and non-fast-forward updates. It still requires zero approving reviews and does not require code-owner review. To change that, a repository administrator must edit the `Protect main` ruleset under Settings → Rules → Rulesets, set at least one approval, enable code-owner review and stale-review dismissal, retain the existing required check and restrictions, and assign an eligible independent reviewer in CODEOWNERS. Verify enforcement with a test PR touching a protected path. If no independent reviewer exists, use the separately administered external check described above; do not configure the author as a substitute for independent approval.

The full dependency audit on 2026-10-29 reported moderate GHSA-67mh-4wv8-2f99 in the development-time esbuild dependency of drizzle-kit and low GHSA-gcqx-w48m-w2h4 in deepmerge. The latter reported no published fix. The high-severity CI gate passing does not resolve these findings; assess upstream compatibility before overrides and avoid exposing development servers to untrusted networks.
