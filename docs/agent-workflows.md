# Agent workflows

`AGENTS.md` is the shared policy for Codex, Claude Code and OpenCode. Claude has native project permissions and a tested PreToolUse hook; it leaves ordinary push verification to Git's pre-push hook. Hook exit 2 blocks, exit 0 allows or returns an ask decision. Claude may treat other hook failures as nonblocking, so native permissions and sandboxing remain essential. Codex uses `AGENTS.md`, its native sandbox and approvals, and the common Git hooks; repository instructions alone cannot enforce them. No configuration here disables the user's sandbox or approvals.

OpenCode's project configuration sets `worktree.directory` to `../fleck-home-hub-worktrees`. OpenCode resolves it relative to the project's saved canonical checkout, then appends the worktree name; existing worktrees are not moved. Other agents should use the same sibling directory for newly created worktrees when practical. For example, from the canonical checkout, `git worktree add -b feature/example ../fleck-home-hub-worktrees/example origin/main` creates a feature worktree after fetching main. Check `git worktree list` and avoid existing paths or branches before creating one. Run the project's bootstrap in the new worktree to install dependencies and configure its hooks.

OpenCode can create a worktree with a detached HEAD. Before starting work there, check `git status` and `git branch --show-current`, verify that HEAD is based on the intended current main, and create a named feature branch with `git switch -c feature/example`. Choose an unused branch name and preserve existing changes; do not reset or discard work. The approval plugin requires a named non-default branch for trusted-worktree operations, so a detached worktree will otherwise prompt for approval.

Automatic approval also requires the checkout and worktree to be inside a user-configured trusted root, a trusted remote and an unchanged tracked scripts directory; this location alone grants no approval. If the canonical checkout is outside that root, the sibling directory may be outside it too. Ask the user before changing global trust or agent configuration; do not widen it to make a worktree qualify. See the [OpenCode worktree configuration](https://opencode.ai/v2/docs/config#worktrees) for path resolution and precedence.

OpenCode Desktop can install a CLI at `~/.opencode/bin/opencode`, which can be invoked by its full path if it is not on the current shell's PATH. Run it with `--version` to check the installed version; a new terminal may be needed after installation. If the CLI is not installed, on macOS `ps -axo pid,comm | rg '[o]pencode-cli'` can identify the desktop service's bundled executable, whose versioned path can change after an update. See the [CLI documentation](https://opencode.ai/v2/docs/cli#paths). Do not restart a running service or change the user's PATH without authorization.

After a rebase the user requested, `./scripts/push-branch.sh` publishes the current feature branch without prompting: it takes no arguments, refuses `main`, `master`, a detached HEAD, a dirty tree and a branch that lacks the latest `origin/main`, and pushes `HEAD` to the same branch name. If that branch already has a remote-tracking ref it uses a lease pinned to that ref, which only `git fetch origin main` in the script leaves untouched, so a commit someone else pushed fails the lease. Hand-written lease pushes still ask. With user authorization, a feature branch may be rewritten using an explicit `--force-with-lease=<full-ref>:<reviewed-remote-commit>` and a single matching branch refspec. Inspect the remote commit before rewriting and stop if the lease fails; do not merely refresh the expected value and retry. Explicit expected commits avoid background fetches weakening the lease. The pre-push hook protects branch destinations and runs verification, but Git does not tell it whether a lease was supplied. GitHub's independently configured branch protections remain necessary. Claude asks before a lease push; OpenCode's shell ask and plugin behavior depend on its effective configuration and are not guaranteed human approval.

OpenCode V2 rules are ordered, with later matching rules taking precedence; project, global and agent scopes must be reviewed together. Project hard policies add limited denials; native security policies and human approval remain necessary. Sharing is disabled. The `/work-issue` and `/ship` commands follow the shared workflow and never approve or merge a PR.

The project keeps a shell-wide ask as the baseline, and the routine allowlist lives under `agents.build.permissions`: global rules are appended after project rules and the last match wins, so a project-level allow would be overridden by a user-level shell ask. The build agent allows read-only inspection (`rg`, `grep`, `sed -n`, `cat`, `ls`, `find`, read-only Git including `git -C <path>`), `git add`/`commit`/`fetch`/`push`, `git worktree add`, `gh issue`/`gh pr`, the fixed-table `./scripts/dev.sh`, `sync-main.sh` and `push-branch.sh`, and external-directory access to the canonical checkout, the sibling worktree directory and OpenCode's per-user scratch directory under `/var/folders/*/*/T/opencode`. Later rules re-ask or deny force pushes, `gh pr merge` and approvals, branch deletion, `.env` and database reads, hard resets, `git clean`, `sudo`, `pkill` and `tailscale`; force-with-lease pushes still ask. Named `mise run` tasks (`test`, `e2e`, `typecheck`, `lint`, `build`, `verify`, `doctor`, `agent-policy`) and the project's test runners (`pnpm vitest run`, `pnpm exec playwright test`) are allowed with arguments, as are the same test, lint, typecheck, e2e and build runners through `./scripts/run-with-mise.sh`; they run repo-defined code, as `dev.sh` does. The wrapper itself runs any command, so every other form of it, other `mise` and `pnpm` commands, and interpreters stay on ask. The policy parity check rejects any project-level shell allow, wildcard action allows, a missing shell-wide ask rule, a build-agent allow of a shell-wide wildcard, interpreter or command runner, and a build agent that does not finally deny merge, force push, hard reset and clean. It checks repository configuration only: it cannot verify OpenCode's effective merged configuration, saved approvals, scanner, plugin, or independently controlled global hard policies. A shell ask can be automatically approved by the plugin, so it is not a hard security boundary. The documented V2 matching rules and precedence are at https://opencode.ai/v2/docs/permissions. Keep the plugin, its configuration, credentials, and any native hard policies outside agent-writable paths; require an independent human for changes. Do not rely on spelling-based project patterns to block every force-push, shell composition, credential read, or destructive operation.

To validate an installation without household data, use a disposable OS account or isolated machine with a synthetic Git repository, synthetic paths, and a separately reviewed temporary configuration. Confirm the effective OpenCode version and configuration sources, then test alternate Git option orderings, `--force-with-lease`, branch deletion, shell composition, private-file paths, external paths, and script changes. Verify native hard denies cannot reach automatic approval, and verify reviewer timeout, unavailable key, malformed output, or failure requests a human decision. Inspect only sanitized decision metadata. Do not test by reading real secrets or modifying the user's global configuration. Until these checks have actually passed on the installed version and plugin, their effective behavior remains unverified.

The existing [OpenCode approval plugin](https://github.com/a1flecke/opencode-auto-approval) is user-owned. Its model reviewer is an aid, not a security boundary: hard deny, deterministic permissions, then model review for asks. Failure, missing credentials, invalid output, timeout and uncertainty must ask a human. `./scripts/setup-opencode-local.sh` checks only project/CLI presence; it cannot prove plugin readiness and never reads global credential files.

The plugin's README currently describes installation from a clone, while this project's requested policy requires a verified release rather than a development checkout. Resolve that discrepancy before installing or updating: review the exact release and its entry point, verify the artifact's checksum and GitHub attestation, and use an immutable, versioned location outside the auto-discovery `plugins` directory. Do not assume a release artifact has the same layout as the source checkout. The human must review the minimal global configuration change, preserve a rollback, and restart only when idle. If provenance, compatibility, or installation instructions are unclear, stop for human review. Configure trusted roots manually and verify the active plugin identity and decisions without exposing credentials.

Only fixed-behavior scripts with reviewed arguments are candidates for `trustedScripts`. The dispatcher and sync/push helpers are candidates for human review, not automatically trusted; a trusted script and its directory must satisfy the plugin's integrity requirements. Never trust `scripts/run-with-mise.sh`, which executes arbitrary commands. Do not add trust entries on the user's behalf.
