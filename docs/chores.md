# Chores and verified earnings

Parents can assign a one-off chore or schedule recurring chores for a child in the same household. A child can submit a to-do or returned chore; submission moves it to pending verification and does not create earnings. A parent can verify the submission or return it with an optional reason. The child can submit returned work again. Recurring schedules create separately verified occurrences; see [architecture](architecture.md) for scheduling and editing details.

Verification updates the chore, writes the transition actor and time, and creates a credit for a positive reward in one SQLite transaction. A unique chore association prevents duplicate credits; ledger updates and deletes are rejected. The verified amount is a snapshot in integer cents, and earned balances are derived from credits. An unpaid chore creates no credit. Parents can configure a payday reminder and record payments already made; the app does not transfer money. See [architecture](architecture.md) for payout, correction and balance behavior.

Active parents can visit `/chores/recovery` to review missing scheduled dates from the previous 30 household-local calendar days, one active recurring chore at a time. Dates with existing occurrences, skips, or recorded pauses are excluded. A gap does not tell you whether work was done. Earlier pause and reward history may be incomplete, and the displayed child and reward are the current series values.

Active parents can also open `/chores/week`, a phone-friendly board for one Sunday-to-Saturday household-local week. It groups chores by day and child, shows due date, reward or **No reward**, verification status and whether the work repeats, and links to the review queue, chore history and recurring schedules. Previous week, This week, Next week and a direct date jump move between weeks without JavaScript. Child and status filters preserve the selected week. Quick add creates an ordinary one-time chore that starts as To do; it never creates earnings. An empty week offers **Add the first chore**, and a rejected submission keeps the entered details and the selected week for correction. The board reads only the selected seven dates, caps a very busy week at 500 rows, and generates recurring occurrences only from today or a future selected week through that week's end. It never backfills a past week; use recovery for historical gaps. See the [mobile board](screenshots/chore-week-mobile.png), [desktop board](screenshots/chore-week-desktop.png) and [empty week](screenshots/chore-week-empty-mobile.png).


Leave a date alone to revisit it while it remains in the review window. Skipping records a permanent exception. Creating a late chore requires confirming the child and entering a fixed reward, including zero for unpaid work. Each decision records who made it and when. A late chore becomes an ordinary to-do and only earns a credit after the child submits it and a parent verifies it.

Before migrating a real database, stop the service and make and verify a backup as described in `deployment.md`. Run `mise run migrate` to apply the checked-in household migration; the Better Auth schema is unchanged. The migration tests cover a fresh database and an existing synthetic household.

For a synthetic demonstration, run `mise exec -- pnpm exec tsx scripts/e2e-server.ts` and open `http://127.0.0.1:4173`. The temporary database contains `parent@example.test` / `synthetic-parent-password` and `kid@example.test` / `synthetic-kid-password`; it is deleted when the test server exits. Run `mise run e2e` for the automated mobile journeys. These accounts and passwords are test fixtures only and must never be used for a real household. There is no second-parent provisioning interface yet.
