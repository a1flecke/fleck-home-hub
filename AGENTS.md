# Fleck Home Hub agent policy

Fleck Home Hub is a private, self-hosted household application. Keep it a modular monolith: presentation calls application services; domain rules do not depend on UI or persistence; infrastructure implements concrete adapters. Do not invent abstractions for unimplemented domains.

Preserve an acyclic dependency direction: domain rules remain independent of framework, infrastructure, and presentation; server services do not import routes; client runtime code does not import server-only modules. This keeps business rules testable without a UI or database and prevents private server behavior from entering client code. Run the architecture tests when changing modules, imports, aliases, or toolchain configuration; add negative fixtures when extending their rules so a missing dependency cannot silently pass. The graph checks are a backstop, not proof of sound design or authorization: review untracked dynamic imports, framework-generated modules, type-only dependencies, and new alias resolution explicitly. Use the domain vocabulary in [architecture](docs/architecture.md), and change its behavioral tests when the meaning of a term or state changes; avoid brittle keyword bans and speculative layers.

Use test-driven development for meaningful behavior: write a focused test, run it and confirm it fails for the intended reason, implement the smallest correct change, and refactor while keeping it green. Choose tests by risk and behavior, not coverage quotas. Follow the test pyramid in [testing and frontend practice](docs/testing-and-frontend.md): prefer fast unit tests for domain rules, real integration tests for authorization, database and framework boundaries, and a few browser journeys for behavior lower layers cannot prove. Before implementing, identify ordinary success, rejection, state-change and recovery paths relevant to the change; include the resulting evidence in review. Do not duplicate the same cases at every layer or mock away the boundary under test. Test authorization at the server boundary, including anonymous, child, and cross-household access. A child chore submission is pending until a parent verifies it; only verification may create exactly one reward credit.

For server-rendered interactive controls, provide a native form/link fallback or keep the control disabled until its JavaScript handler is ready. Test the pre-hydration boundary deterministically with JavaScript disabled or delayed. For editable fields, including initially empty fields, use the project's Svelte binding pattern and delay hydration while changing representative input types, checkboxes and selections; verify the edits survive hydration and appear in submitted form data. A static value attribute can overwrite early edits, and a JavaScript-disabled test alone does not establish hydration safety. Also verify that disclosures opened before hydration remain open and usable afterward. Browser tests must assert each mutation's visible result before navigating away, scope locators to the affected record, and use distinct synthetic records when repeating scenarios. Investigate flakes from traces and reproduce their cause; do not mask them with sleeps, retries, or larger timeouts. A green PR run is evidence for that run, not proof of stability or of post-merge main CI; report both separately.

Inventory every new or changed form and filter, including nested forms and dynamically rendered checkbox groups. A hydration test for one form does not cover another form on the same page. For each distinct editable control group, exercise a change before hydration, confirm its submitted form data afterward, and cover restored values after validation when applicable. In Svelte, prefer `bind:value`, `bind:checked` or `bind:group` for editable reactive defaults; a reactive `value` or `checked` attribute may reset input on hydration. Check existing neighboring controls for the same pattern and test suspected cases before changing them.

Keep the source tree stable while browser tests run: edits to watched files can trigger a development-server reload that interrupts unrelated navigation. Finish edits before starting the suite and wait for it to exit before changing files. If a reload or restart occurs, inspect its timing and trace rather than attributing the failure to the application without evidence.

When adding forms or controls, inspect neighboring browser tests for page-wide partial-label selectors that may also match the new controls. Scope form interactions to their named section or intended record and use exact accessible names where appropriate; do not select forms by page-wide position. Exercise repeated scenarios with existing records present. Run the existing workflows for the changed page as well as the new scenario; a passing new scenario alone does not establish that existing workflows still work.

Browser tests that assert household-wide or per-person totals must use synthetic data isolated from concurrently running tests. Distinct record names alone do not isolate shared balances; preserve exact assertions and investigate shared-state interference instead of adding retries or weakening them.

For editable forms, test an invalid submission and correction through the browser: preserve the entered values, keep the relevant form available, and provide an actionable error without losing unrelated data. Check the same behavior for native submissions as well as any enhanced path.

When a form lives on a filtered or date-selected page, inspect how its action URL and subsequent navigation carry the selected context. A relative named action can replace the whole query string. Test both rejected and successful submissions on a non-default filter, and verify the saved record remains visible; when an edit changes the record's date or filter, verify navigation reaches its new context. Apply this to native and enhanced submissions as appropriate. Review neighboring forms for the same context loss before introducing a new pattern.

When projecting existing records into a shared view, test the entire server response for excluded private fields and non-shared records, not just visible cards. Exercise source-record state changes such as cancellation, skips and revocation so the projection follows the same domain rules as the original view.

For automatically updated views, avoid timed full-page refreshes that interrupt reading or keyboard focus. Provide a way to pause updates and a usable native refresh fallback, and test data freshness with a controlled clock. Before advancing a fake clock, assert that hydration has initialized the timer using an observable readiness signal; server-rendered content can appear before the timer exists. Test network failure and recovery rather than assuming a framework refresh API rejects its promise when a load fails.

After sign-in, assert the authenticated page or session is ready before taking storage state or sending dependent requests. When testing SvelteKit form actions through an API client, assert the action response type and application status as well as HTTP status: redirects can be encoded in a successful HTTP response. Use valid, authorized fixtures for negative authorization tests so input validation or an anonymous redirect cannot masquerade as an authorization check.

Use mise as the tool-version authority: `MISE_LOCKED_SCOPES=project mise install --locked`, `mise run install`, `mise run dev`, `mise run lint`, `mise run typecheck`, `mise run test`, `mise run build`, `mise run e2e`, and `mise run parity`. The scope applies locked mode to project tools without requiring unrelated global tools to be in the project lockfile. Global tools can still be installed without this lock check; see the development guide. Run focused tests first and the complete required checks before delivery. Report checks that did not run.

Preserve pnpm's three-day release cooldown and default-deny dependency build policy. Review any exception or build-script approval against the exact dependency and explain why it is necessary; do not weaken the policy to make an install pass. Revalidate the frozen lockfile and test affected native dependencies after changing these settings. These controls reduce exposure to newly compromised releases and unreviewed install-time code; they do not replace dependency review or advisory scanning.

Before adding framework imports or APIs, check the pinned framework version, project configuration and a working neighboring example; do not assume an alias from another version exists. For dynamic external links, validate allowed URL schemes server-side and follow the pinned SvelteKit and lint conventions for external navigation. Run `mise run lint` and `mise run typecheck` after changing routes, templates, or imports and before browser workflows, so failures are caught at the narrowest useful boundary. Fix ordinary lint errors without asking for permission; ask before suppressing a lint rule, adding an exception, or disabling lint.

Read the issue and relevant code before changes. Work on a feature branch or isolated worktree; never commit or push directly to main. Put new worktrees in the sibling directory described in [agent workflows](docs/agent-workflows.md), unless the user specifies another location. Preserve unrelated changes. Review the complete diff, verify the work, commit, and open a PR. Never merge or approve your own PR, force-push a protected branch, delete a protected branch, or bypass failed checks. Rewrite a feature branch only with user authorization and `--force-with-lease=<full-ref>:<reviewed-remote-commit>` for that one branch; inspect the remote commit before rewriting and stop if the lease fails. Never use plain force. After a rebase the user asked for, publish the branch with `./scripts/push-branch.sh`, which pushes only the current feature branch with a lease pinned to the remote tip this clone last saw, and refuses main, a dirty tree, or a branch missing the latest `origin/main`; do not hand-write lease pushes. Ask the user before deployment, destructive operations, changing global machine or agent configuration, or accessing unrelated private directories. Never run broad process termination commands.

Treat household information, local databases, environment files, authentication secrets, and backups as private. Use only synthetic fixtures. Do not read, print, copy, or commit credentials or private household data. Never alter the user's global OpenCode configuration or install an approval plugin. Native sandbox and approval controls, Git hooks, and CI each provide separate safeguards; repository instructions do not replace them.

Keep documentation accurate and concise. Record material architecture and security decisions. State risks and limitations honestly, especially untested remote access, platform behavior, and branch protections. Do not claim validation or enforcement without evidence.
