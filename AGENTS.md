# Fleck Home Hub agent policy

Fleck Home Hub is a private, self-hosted household application. Keep it a modular monolith: presentation calls application services; domain rules do not depend on UI or persistence; infrastructure implements concrete adapters. Do not invent abstractions for unimplemented domains.

Preserve an acyclic dependency direction: domain rules remain independent of framework, infrastructure, and presentation; server services do not import routes; client runtime code does not import server-only modules. This keeps business rules testable without a UI or database and prevents private server behavior from entering client code. Run the architecture tests when changing modules, imports, aliases, or toolchain configuration; add negative fixtures when extending their rules so a missing dependency cannot silently pass. The graph checks are a backstop, not proof of sound design or authorization: review untracked dynamic imports, framework-generated modules, type-only dependencies, and new alias resolution explicitly. Use the domain vocabulary in [architecture](docs/architecture.md), and change its behavioral tests when the meaning of a term or state changes; avoid brittle keyword bans and speculative layers.

Use test-driven development for meaningful behavior: write a focused test, run it and confirm it fails for the intended reason, implement the smallest correct change, and refactor while keeping it green. Choose tests by risk and behavior, not coverage quotas. Follow the test pyramid in [testing and frontend practice](docs/testing-and-frontend.md): prefer fast unit tests for domain rules, real integration tests for authorization, database and framework boundaries, and a few browser journeys for behavior lower layers cannot prove. Before implementing, identify ordinary success, rejection, state-change and recovery paths relevant to the change; include the resulting evidence in review. Do not duplicate the same cases at every layer or mock away the boundary under test. Test authorization at the server boundary, including anonymous, child, and cross-household access. A child chore submission is pending until a parent verifies it; only verification may create exactly one reward credit.

For server-rendered interactive controls, provide a native form/link fallback or keep the control disabled until its JavaScript handler is ready. Test the pre-hydration boundary deterministically with JavaScript disabled or delayed. For editable fields, including initially empty fields, delay hydration while changing representative input types, checkboxes and selections; verify the edits survive hydration and appear in submitted form data. Also select a prefilled value before hydration and finish replacing it afterward: initialization may disturb an active selection even when completed edits survive. A JavaScript-disabled test or waiting for network idle alone does not establish hydration safety. Also verify that disclosures opened before hydration remain open and usable afterward. Browser tests must assert each mutation's visible result before navigating away, scope locators to the affected record, and use distinct synthetic records when repeating scenarios. Investigate flakes from traces and reproduce their cause; do not mask them with sleeps, retries, or larger timeouts. A green PR run is evidence for that run, not proof of stability or of post-merge main CI; report both separately.

Inventory every new or changed form and filter, including nested forms and dynamically rendered checkbox groups. A hydration test for one form does not cover another form on the same page. For each distinct editable control group, exercise a change before hydration, confirm its submitted form data afterward, and cover restored values after validation when applicable. In Svelte, select bindings or native defaults based on the control's actual reactive needs; neither a binding nor a reactive `value` attribute alone proves hydration safety. For controls whose state is only read on submit, start with native `defaultValue` and `defaultChecked`. A reactive `checked` can overwrite a change made before hydration and silently alter what the form submits. Check rejected values in the native HTML response as well: on our pinned Svelte version a textarea’s default is its rendered text, and setting its DOM default alone does not restore it on a native POST. Use native disclosure state for user-opened panels and check the serialized form payload after hydration. Test dirty values, active selection and validation recovery, and check neighboring controls for the same pattern.

Playwright waits for browser navigations, not SvelteKit client-side navigations: after a link click or GET-form submission, `click()` returns while the outgoing page is still rendered, and SvelteKit blurs the focused element when the navigation lands. After every navigating click, `await settle(page)` (`e2e/support/navigation.ts`) before the next interaction or read; a content assertion or `toHaveURL` is not a substitute, because the content can exist on both pages and SvelteKit updates the URL before the DOM. Never use a non-waiting read such as `count()` as a loop condition after a navigation without settling first. Mark a deliberate exception with `// no-settle: <reason>`. `tests/architecture/e2e-navigation-settle.test.ts` enforces this. Diagnose a browser failure from its trace (action timeline, DOM snapshots, network) before naming a cause: "element was detached" and a test timeout are symptoms, and the reported line is only the action that was running when time ran out.

Browser tests must be repeatable. Build every household a new spec touches with `freshHousehold()` (`e2e/support/households.ts`) and mark the file `// e2e-isolation: fresh-households`; do not add tests to the shared seeded households in `scripts/e2e-server.ts`. `tests/architecture/e2e-isolation.test.ts` keeps marked specs off shared seeded accounts and ratchets `LEGACY_SHARED_SPECS`, which may only shrink: migrate a legacy spec rather than extending it, then remove it from the list. `mise run e2e-repeat` (run in CI) runs the marked specs twice in one server. The seeding service is test infrastructure in `scripts/`; never add a seeding or test-only route to the application. It writes each household in one `BEGIN IMMEDIATE` transaction because the app writes the same SQLite file from another process.

Browser tests run against production builds: `mise run e2e` and `mise run e2e-repeat` build each test server's app with `scripts/e2e-prepare.mjs` into `.e2e-build/` (never `build/`) because `AUTH_ORIGIN` is a build-time input, then run it with `node`. `E2E_SERVER=dev` runs `vite dev` instead, for debugging only; a passing dev run does not establish production behaviour. Gate a page's client module for pre-hydration tests with `pageModule(route)` (`e2e/support/modules.ts`), never a `src/routes` URL, which only exists under `vite dev`. Assert behaviour that holds in a production build: SvelteKit rejects cross-site and origin-less form POSTs with 403 before an action runs, and a build with `paths.origin` renders asset links absolute.

Write browser-test screenshots through Playwright's `testInfo.outputPath(...)`. Routine verification must leave tracked documentation and other source files untouched. Refresh committed screenshots in a dedicated capture step.

Keep the source tree stable while browser tests run: edits to watched files can trigger a development-server reload that interrupts unrelated navigation. Finish edits before starting the suite and wait for it to exit before changing files. If a reload or restart occurs, inspect its timing and trace rather than attributing the failure to the application without evidence.

When adding forms, controls, status regions or alerts, inspect existing browser tests for ambiguous page-wide selectors, including workflows that arrive from another route. Scope form interactions to their named section or intended record and use exact accessible names where appropriate. Scope status and alert assertions to their specific text or region, and exercise mutation feedback after hydration when live notices can coexist with it. Avoid using page-wide position to disambiguate matches. Exercise repeated scenarios with existing records present. Run the existing workflows for the changed page as well as the new scenario; a passing new scenario alone does not establish that existing workflows still work.

Browser tests that assert household-wide or per-person totals must use synthetic data isolated from concurrently running tests. Distinct record names alone do not isolate shared balances; preserve exact assertions and investigate shared-state interference instead of adding retries or weakening them.

For editable forms, test an invalid submission and correction through the browser: preserve the entered values, keep the relevant form available, and provide an actionable error without losing unrelated data. Check the same behavior for native submissions as well as any enhanced path. When a rejection test needs to forge a hidden or server-managed value, alter the serialized request and assert the server rejection before retrying. Direct DOM edits to those values can be overwritten during hydration and accidentally submit a valid mutation. Keep the submitted version attached to every retained draft, including after validation errors. Freshly loaded data can show the current version alongside the draft, but must never silently supply that version to its save form. In a two-session test, resubmit the rejected draft unchanged and verify that it is still rejected and the other session’s change survives.

When a form lives on a filtered or date-selected page, inspect how its action URL and subsequent navigation carry the selected context. A relative named action can replace the whole query string. Test both rejected and successful submissions on a non-default filter, and verify the saved record remains visible; when an edit changes the record's date or filter, verify navigation reaches its new context. Apply this to native and enhanced submissions as appropriate. Review neighboring forms for the same context loss before introducing a new pattern. `tests/architecture/form-context.test.ts` rejects bare named actions on routes that read query context, including a selected household; it cannot see an action that carries only part of the query, so check every parameter the route reads.

When projecting existing records into a shared view, test the entire server response for excluded private fields and non-shared records, not just visible cards. Exercise source-record state changes such as cancellation, skips and revocation so the projection follows the same domain rules as the original view.

For automatically updated views, avoid timed full-page refreshes that interrupt reading or keyboard focus. Provide a way to pause updates and a usable native refresh fallback, and test data freshness with a controlled clock. Before advancing a fake clock, assert that hydration has initialized the timer using an observable readiness signal; server-rendered content can appear before the timer exists. Test network failure and recovery rather than assuming a framework refresh API rejects its promise when a load fails.

After sign-in, assert the authenticated page or session is ready before taking storage state or sending dependent requests. When testing SvelteKit form actions through an API client, assert the action response type and application status as well as HTTP status: redirects can be encoded in a successful HTTP response. Use valid, authorized fixtures for negative authorization tests so input validation or an anonymous redirect cannot masquerade as an authorization check.

When sign-in is browser-test setup, authenticate through the real sign-in API with the browser context's request client and check its response. Exercise the sign-in form in journeys that cover authentication behavior. When a test requires separate sessions, authenticate each context independently and verify that the sessions differ. Copying storage state reuses the same session. For sign-in timeouts, use the trace to distinguish a pending or rejected auth request from a delay after authentication.

Use mise as the tool-version authority: `MISE_LOCKED_SCOPES=project mise install --locked`, `mise run install`, `mise run dev`, `mise run lint`, `mise run typecheck`, `mise run test`, `mise run build`, `mise run e2e`, and `mise run parity`. The scope applies locked mode to project tools without requiring unrelated global tools to be in the project lockfile. Global tools can still be installed without this lock check; see the development guide. Run focused tests first and the complete required checks before delivery. Report checks that did not run.

For a fresh checkout or worktree, run `./scripts/bootstrap.sh`: locked tools, frozen dependencies, SvelteKit sync, hooks, then doctor. Use the package-backed test helpers (`./scripts/dev.sh test tests/<file>.test.ts`, `mise run test`, `./scripts/dev.sh e2e e2e/<file>.spec.ts`, or `mise run e2e`); they generate SvelteKit configuration before loading the runner. Do not assume a previous typecheck, build or dev server generated `$app/tsconfig`. Direct Vitest, Playwright or TypeScript-runner commands require `mise exec -- pnpm exec svelte-kit sync` first. After changing setup or test runners, exercise the disposable cold-start regression before the full checks; never remove generated files from a checkout with active tests or a dev server. Treat several suites failing at configuration load as one shared setup failure: investigate that prerequisite before retrying the suites.

When a test times out, capture the underlying error or exit status and compare its elapsed time in isolation and under the normal parallel runner. For whole-application scans and tests that launch compilers or nested runners, keep the test worker responsive and give the operation a deadline shorter than the test's. Justify any test-local timeout with measurements under representative load. For server or worker readiness, handle startup errors and exits before readiness, and clean up resources on success, failure and timeout. Exercise a forced startup failure when changing these helpers. Keep architecture rules, negative fixtures and verification coverage intact. Avoid retries, sleeps and global timeout increases as substitutes for fixing the cause.

Migration upgrade fixtures must use a contiguous journal prefix ending at a named boundary. Never maintain an exclusion list of newer migrations: a future entry can make Drizzle skip the missing history. Assert the baseline lacks the target schema and add a regression showing future journal entries do not change the baseline. Investigate fixture and application failures separately. When rebasing or merging migration work, preserve the entries already on main, give new entries consecutive indexes and strictly increasing `when` values, and test the upgrade from the latest migration on main. Drizzle can skip a new migration when its timestamp matches the last applied entry. Run the neighboring upgrade tests as well.

For household writes, check active membership after obtaining the SQLite writer lock, in the same transaction as the mutation, and read any source rows the mutation depends on inside that same transaction. Route authorization is an early rejection only. Check alternate branches such as duplicate confirmation and idempotent returns, and prove revocation wins with two connections and a controlled barrier. Keep `tests/architecture/write-transaction-auth.test.ts` green when adding or modifying immediate write transactions or recurring-series visibility filters.

For recurring or pre-generated work, lifecycle transitions (`paused`, `ended`) must not rely on comparing `scheduled_date >= today` alone: anchor paused visibility and submission guards to `paused_on`, and cancel unstarted occurrences from the end cutoff onward when ending a series so advancing clocks never resurrect hidden chores as overdue. Schedule revisions must never overwrite `recurring_series.start_date`; store effective-dated versions in `recurring_series_version` so pre-effective-date generation, skips, recovery, and earlier revisions stay intact. Archiving cancelled recurring occurrences must set `recurring_occurrence.archived_at` (with active uniqueness enforced by `WHERE archived_at IS NULL`) so re-adding a previously removed weekday creates a fresh occurrence without deleting cancelled chore history. Schedule previews and revisions must evaluate every materialized future occurrence (using `dateMatchesSchedule` with no 366-day upper date cap or `LIMIT`) so far-future occurrences are cancelled when weekdays change or `endDate` shortens. Household-wide verified balance summaries (such as `reviewChildSummaries`) must enumerate active children from `active_membership` rather than grouping only over pending submissions so children with zero pending work are never omitted from owed totals. Keep `tests/architecture/recurring-invariants.test.ts` green when changing recurring schedules or verification summaries. For idempotent batch creation (`createReuseBatch`), validate and normalize inputs before checking the idempotency table and compare every stored payload field on key reuse (rejecting mismatches with `key-conflict` / 409 and issuing a fresh key). For bounded filtered views (`loadChoreWeek`), compute whole-week aggregates via SQL `GROUP BY` and apply filters in SQL `WHERE` before `LIMIT`. Keep `tests/architecture/chore-board-and-reuse-invariants.test.ts` green when changing chore reuse or the weekly chore board. At the `/api/auth/*` boundary, require at least one `active_membership` row on email sign-in and account-mutation endpoints so disabled accounts cannot re-authenticate or alter live-joined `user` records.

For SQLite mutations that await framework work, inventory every caller and fixture before changing the service contract. Use a temporary file-backed database for worker and multi-connection tests because ordinary in-memory SQLite connections do not share data. Keep the authorization recheck, related writes and awaited framework operation on the same connection inside one transaction. Never pass an async callback to better-sqlite3's synchronous transaction helper or hold a writer lock on the HTTP thread while awaiting work that needs that lock. Keep one production mutation path. Verify commit and rollback through real sessions, including a forced late failure and another active household. Review the packaged worker entry point and send only the configuration it needs.

For date-sensitive fixtures, seed dates in the same explicit time zone the feature uses. Control the clock at a UTC and local date boundary when testing date selection.

For effective-dated or versioned records, test an edit against a past, a same-day and a future occurrence, and cover single-occurrence plans as well as recurring ones. Records that describe something already done, such as payments and payouts, must reject household-local future dates at the service boundary.

When a security or safety control is enabled by a dependency from an environment variable, such as Better Auth's sign-in limiter and `NODE_ENV`, verify it in the environment the real launcher provides (`scripts/pilot/launch.sh` then `scripts/start.sh`), not only by forcing the variable in a test. Prefer failing closed when the variable is missing, and assert the control with it unset. A test that sets the variable itself proves only the forced case.

For name-matching heuristics, test each rule in both directions with paired matching and non-matching examples, including plurals of words that already end in e or ie. When reviewing or confirming editable grocery proposals (meal handoff, week shop, and bulk add), match against the submitted/overridden item name via `matchesActiveGrocery` (not the original unedited line once renamed), do not validate skipped rows, and exclude skipped rows from within-batch duplicate tracking. When un-completing a checklist item (`completed = false`), clear `completed_by` and `completed_at` to `NULL` and gate UI completion attribution on `item.completed && item.completedAt`. Keep `tests/architecture/grocery-and-checklist-invariants.test.ts` green when changing grocery review/confirm flows or checklist completion. For recurring calendar events and recurring chore series, validate `hasRecurrenceOccurrence(...)` so zero-occurrence schedules are rejected; `cancelOccurrence` must require `calendar_event.weekdays IS NOT NULL` so one-off events cannot become phantom uncancelled rows. In `src/lib/grocery/ingredient-parser.ts`, check percentage product prefixes (`2 % milk`) before `quantityPattern` and share `numberAtom` across range, sum, alternative, and compound-remainder guards so fractions/decimals stay flagged `needsReview: true`. Keep `tests/architecture/calendar-and-parser-invariants.test.ts` green when editing calendar recurrence/exceptions or ingredient parsing.

For SQLite backup and restore, treat the database and its WAL, SHM and rollback journal as related paths. Verify copies in private staging and publish a complete artifact without overwriting the destination. Use real SQLite fixtures to exercise existing companion files, uncheckpointed writes, a path created during the copy and failed-copy cleanup. Assert what remains on disk as well as the exit or error status.

Preserve pnpm's three-day release cooldown and default-deny dependency build policy. Review any exception or build-script approval against the exact dependency and explain why it is necessary; do not weaken the policy to make an install pass. Revalidate the frozen lockfile and test affected native dependencies after changing these settings. These controls reduce exposure to newly compromised releases and unreviewed install-time code; they do not replace dependency review or advisory scanning.

Run CI's dependency audit, `mise exec -- pnpm audit --audit-level moderate`, on the current lockfile before expensive verification and refresh it before publishing if the lockfile changed or the result is stale. Advisories can become blocking without a dependency change. If CI fails, inspect the first failed step and distinguish the root failure from a dependent merge gate. Review the full audit for related advisories and affected dependency paths. Apply the smallest eligible fixes under the release cooldown, then verify the frozen install and rerun the audit. Record any unresolved advisory and its fix availability. Resolve blocking findings before publishing a review-ready PR.

Before adding framework imports or APIs, check the pinned framework version, project configuration and a working neighboring example; do not assume an alias from another version exists. For internal SvelteKit links with query strings or fragments, pass the full destination to `resolve()`, for example `` href={resolve(`/meals?date=${encodeURIComponent(date)}`)} ``. Appending a query or fragment to the return value triggers `svelte/no-navigation-without-resolve`. Check a working neighbor and, if a lint fix repeats the same diagnostic, inspect the pinned rule or compiler before the next edit. For dynamic external links, validate allowed URL schemes server-side and follow the pinned SvelteKit and lint conventions for external navigation. Run `mise run lint` and `mise run typecheck` after changing routes, templates, or imports and before browser workflows, so failures are caught at the narrowest useful boundary. Fix ordinary lint errors without asking for permission; ask before suppressing a lint rule, adding an exception, or disabling lint.

Read the issue and relevant code before changes. Work on a feature branch or isolated worktree; never commit or push directly to main. Put new worktrees in the sibling directory described in [agent workflows](docs/agent-workflows.md), unless the user specifies another location. Preserve unrelated changes. Review the complete diff, verify the work, commit, and open a PR. Never approve your own PR, force-push a protected branch, delete a protected branch, or bypass failed checks. Never merge a PR without explicit user authorization and green required checks. Rewrite a feature branch only with user authorization and `--force-with-lease=<full-ref>:<reviewed-remote-commit>` for that one branch; inspect the remote commit before rewriting and stop if the lease fails. Never use plain force. After a rebase the user asked for, publish the branch with `./scripts/push-branch.sh`, which pushes only the current feature branch with a lease pinned to the remote tip this clone last saw, and refuses main, a dirty tree, or a branch missing the latest `origin/main`; do not hand-write lease pushes. Ask the user before deployment, destructive operations, changing global machine or agent configuration, or accessing unrelated private directories. Never run broad process termination commands.

Run one plain shell command per tool call, without `&&`, `;`, command substitution, loops or shell variables, so OpenCode's approval rules can match it; compare outputs in your own reasoning instead of composing them. Prefer these forms, which the project allows for the build agent: `rg` and `git` for lookups; `./scripts/dev.sh test tests/<file>.test.ts` or `./scripts/dev.sh e2e e2e/<file>.spec.ts` for one test file; `mise run test`, `mise run e2e`, `mise run typecheck` and `mise run lint`, with arguments after `--`; `./scripts/sync-main.sh` to merge the latest main; and, after a rebase the user requested, `git rebase origin/main` followed by `./scripts/push-branch.sh`. Anything else, including `pnpm exec` with other tools, asks for approval.

Treat household information, local databases, environment files, authentication secrets, and backups as private. Use only synthetic fixtures. Do not read, print, copy, or commit credentials or private household data. Never alter the user's global agent configuration (such as OpenCode, Claude, Codex, or Antigravity) or install an approval plugin. Native sandbox and approval controls, Git hooks, and CI each provide separate safeguards; repository instructions do not replace them.

Keep documentation accurate and concise. Record material architecture and security decisions. State risks and limitations honestly, especially untested remote access, platform behavior, and branch protections. Do not claim validation or enforcement without evidence.

For untrusted external HTML or text parsing (such as JSON-LD extraction in `src/lib/server/recipe-preview.ts`), avoid backtracking regexes over large payloads—use linear-time scanning and keep pathological-input timing tests in place. Never render a copyable `readonly` link or token inside `<input type="password">` or with a reactive `value={...}` attribute (enforced by `tests/architecture/readonly-copyable.test.ts`): real browsers mask password inputs and block clipboard copying, and reactive `value` makes Svelte reassign `input.value` during hydration and collapse an active selection before the user can copy it. Apply `Cache-Control: no-store` default-deny for all dynamic routes and `__data.json` endpoints via `applySecurityHeaders` in `src/lib/server/security-headers.ts` rather than maintaining a manual route allowlist in `src/hooks.server.ts`. Never poll `/display/data` or redirect to `/sign-in` when `/display` is in `unpaired` mode; only member-mode display sessions may redirect to `/sign-in`. Keep `tests/architecture/security-and-draft-invariants.test.ts` green when editing `hooks.server.ts`, `/chores/recovery`, or `/display`. Guard every route/helper call to `getIdentityServices()` with `try/catch` returning HTTP `503` (never an unhandled 500), and never return `fail()`/`ActionFailure` from a SvelteKit `PageServerLoad` (throw `error(...)` or `redirect(...)` instead). External NWS weather fetches (`src/lib/weather/nws.ts`) must pass `redirect: 'manual'` and `credentials: 'omit'`, validate any same-origin NWS redirect target, cancel unread bodies on redirect/error, and bound response size (`MAX_NWS_RESPONSE_BYTES`); NWS parsing (`src/lib/weather/nws-parse.ts`) must pass `now` to `parseCurrent` and `timeZone` to `readPeriodStart`. Keep `tests/architecture/routes-and-weather-invariants.test.ts` green when editing `getIdentityServices()` callers, `/settings/sessions`, or NWS weather code. Keep `.agents/hooks/guard.mjs`, `.claude/hooks/guard.mjs`, and `.claude/settings.json` aligned when adding shell or sensitive-file guards.

One bought-grocery clear request may carry at most `MAX_BOUGHT_CLEAR_ROWS` rows (`src/lib/grocery/domain.ts`); the groceries page must build its clear form from `boughtClearBatch(...)` and never submit the entire bought list, or a list over the limit can never be cleared. `src/lib/server/meals.ts` must validate `recipeUrl` with `parseRecipeLink`, the same rule every meal surface uses to display links, so a saved link is never hidden. Every parent settings route and `parentHousehold()` must list households with `parentHouseholds()` in `src/lib/server/parent-household.ts` (active parent memberships only, ordered by name then id) so the default household is identical across routes and a kid membership elsewhere can never cause a 403. Keep `tests/architecture/grocery-meal-and-household-invariants.test.ts` green when changing these.

Every `new Worker(...)` in `src/lib/server/` must pass an explicit minimal `env` object (never inheriting full `process.env`), pass minimal `config: { secret, origin }` (never a raw config object with extra fields), and drain piped streams via `worker.stdout.resume()` and `worker.stderr.resume()`. Routes under `src/routes/` must reuse `getIdentityServices()` rather than opening `new Database(...)` directly, and invitation redemption must trim and bound `name` (`<= 100`), `email` (`<= 254`, non-managed), and `password` (`12..128`). Pilot scripts must inspect `serve.Foreground` for Funnel/Web/TCP entries, enforce `https:` and HTTPS-only TCP termination, compare MagicDNS names case-insensitively (`scripts/pilot/tailscale-check.mjs`), and use `lstatSync` with owner `uid` and non-symlink file/directory checks before `chmodSync`/install/uninstall while rolling back newly written plists on failed bootstrap (`scripts/pilot/launchd.mjs`). Keep `tests/architecture/worker-and-pilot-invariants.test.ts` green when changing workers, `/accept-invitation`, or pilot scripts.
